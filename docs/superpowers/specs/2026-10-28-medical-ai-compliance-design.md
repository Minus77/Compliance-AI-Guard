# 医药行业独立 AI 合规检查网关设计

日期：2026-10-28

状态：已批准（2026-10-28）

## 1. 背景与目标

现有项目具备策略判定、模型候选约束、敏感信息脱敏、提示注入检测、人工复核、
申诉、失败安全、哈希链审计和中英文界面。这些能力主要服务于药品企业现场沟通
文本，业务模型、数据字段和界面仍带有特定工作流假设，不适合直接作为跨企业的
通用 AI 合规产品。

本次改造将产品定位为独立部署的医药行业 AI 合规检查网关。它检查人工提交的
文本，也保护 AI 对话的输入、生成约束和输出。两类入口共享规则库、判定引擎、
人工复核与审计能力。产品无需连接客户关系管理系统、广告系统、药物警戒系统或
任何厂商平台即可完整运行。

### 1.1 目标

1. 提供“内容合规检查”入口，检查提交前和保存前的任意医药行业文本。
2. 提供“AI 对话防护”入口，在模型调用前阻断不合规输入，在生成时注入适用的
   合规约束，并在发布前检查模型输出。
3. 使用一套可配置规则库驱动两类入口，避免规则、严重度、整改建议和审计语义
   分叉。
4. 在检查结果中返回精确字符片段、规则依据、行为、整改建议和复核路径。
5. 允许不同药企、市场、语言、产品和治疗领域配置自己的规则、数据保留策略与
   集成方式。
6. 保留现有确定性判定、模型只能提出候选、人工复核、失败安全和审计链能力。
7. 提供无需外部系统即可运行的本地演示模式，以及面向企业集成的通用连接器
   契约。
8. 同步更新中英文 README、架构、运维、安全、验证和集成文档，删除所有特定
   厂商品牌、产品对象和工作流依赖。

### 1.2 非目标

1. 不构建通用大模型、模型托管平台或企业知识库产品。
2. 不替代医学、法律、药物警戒或监管部门的最终判断。
3. 不宣称完成 GxP、CSV、MLR、药物警戒或目标市场法规验证。
4. 不内置任何单一企业的审批层级、组织编码或数据对象。
5. 不默认保存 AI 对话原文、完整生成结果或敏感信息明文。
6. 不要求部署数据库、消息队列、外部身份提供商或云模型；这些应作为可选
   生产集成。

### 1.3 反目标

1. 不允许模型直接决定严重度、处置或发布权限。
2. 不允许“没有命中规则”被表述为“内容合法”或“监管通过”。
3. 不允许输出检查失败时继续发布未经检查的模型结果。
4. 不允许只靠删除高亮片段来宣称解决合规问题。
5. 不允许一个入口的规则更新在无版本记录的情况下改变另一个入口的历史判定。

## 2. 产品原则

### 2.1 共享核心，双入口

```text
                    ┌──────────────────────┐
                    │ Shared Rule Registry │
                    │ versions / scope     │
                    └──────────┬───────────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
   ┌──────────▼───────────┐         ┌───────────▼────────────┐
   │ Content Compliance   │         │ AI Conversation Guard   │
   │ draft / saved text   │         │ input / generate/output  │
   └──────────┬───────────┘         └───────────┬────────────┘
              │                                 │
              └────────────────┬────────────────┘
                               │
              ┌────────────────▼────────────────┐
              │ Deterministic Decision Engine   │
              │ rules / precedence / spans       │
              └────────────────┬────────────────┘
                               │
       ┌───────────────────────┼───────────────────────┐
       │                       │                       │
 ┌─────▼──────┐        ┌───────▼───────┐       ┌───────▼──────┐
 │ Reviews    │        │ Case Records  │       │ Audit Chain  │
 │ tasks      │        │ versions      │       │ evidence     │
 └────────────┘        └───────────────┘       └──────────────┘
```

服务端仍是唯一有权给出最终判定的一方。模型或规则提取器可以提出命中和改写
候选，但严重度、处置、发布权限、复核要求和审计动作由确定性代码计算。

### 2.2 独立优先

部署分为三种模式：

| 模式 | 必需组件 | 外部系统 | 用途 |
| --- | --- | --- | --- |
| Standalone | 本服务、本地 JSON/JSONL | 无 | 演示、评估、单机试用 |
| Integrated | 本服务、企业身份、持久化存储 | 仅启用所需连接器 | 企业接入 |
| Controlled | 在 Integrated 基础上增加部署加固 | 明确清单与权限边界 | 受控生产环境 |

Standalone 模式必须支持规则管理、内容检查、AI 对话防护、人工复核、审计和
导出。连接器缺失不能阻断这些核心功能。

### 2.3 结果语义

公共结果保持四个处置值：

| 处置 | 含义 | 默认行为 |
| --- | --- | --- |
| `allow` | 当前规则集未发现需要阻断的问题 | 允许继续，但提示“未保证合法” |
| `needs_info` | 缺少完成判断所需信息 | 请求补充，不宣称通过 |
| `human_review` | 发现高风险或需要专业判断的问题 | 进入人工复核 |
| `blocked` | 命中红线规则或检查无法安全完成 | 禁止保存、调用或发布 |

保留 `refused` 作为现有内部终态，用于授权或不可处理请求；普通界面不把它作为
合规结论展示。失败状态 `FAILED_RETRYABLE`、`FAILED_SAFE` 和
`MANUAL_DEGRADED` 继续保留，且任何失败状态都不能生成允许发布的结果。

## 3. 用户与角色

角色从业务岗位改为可配置职能，界面和 API 使用中性名称：

| 角色 | 主要职责 |
| --- | --- |
| `author` | 编写内容或发起 AI 对话 |
| `submitter` | 提交检查并处理补充信息 |
| `reviewer` | 完成常规合规复核 |
| `medical_reviewer` | 复核医学信息与超适应症风险 |
| `safety_reviewer` | 复核不良事件和患者安全信号 |
| `legal_reviewer` | 复核商业行为、利益冲突和法律风险 |
| `compliance_admin` | 配置规则、范围、行为与发布 |
| `auditor` | 查看只读审计与验证链 |
| `admin` | 管理部署、用户和保留策略 |

规则可以要求角色集合，而非固定单人。现有角色枚举可保留兼容别名，但新请求、
默认配置、界面和文档只使用中性角色。授权仍由服务端执行，前端隐藏按钮不能
代替 API 权限检查。

## 4. 内容模型

### 4.1 内容类型

使用稳定、通用的内容类型：

| 类型 | 用途 |
| --- | --- |
| `customer_interaction_note` | 客户互动记录、会议纪要 |
| `medical_information_request` | 医学信息咨询与答复 |
| `medical_field_note` | 医学事务现场记录 |
| `promotional_content` | 推广材料、培训材料、数字内容 |
| `ai_conversation` | AI 对话输入或输出 |
| `other` | 企业自定义内容 |

内容类型决定默认适用的规则包、保留策略和复核角色，但不硬编码任何外部数据
对象。调用方可提供 `content_subtype` 作为自定义细分。

### 4.2 检查上下文

每次检查包含：

- `tenant_id`
- `content_type` 与可选 `content_subtype`
- `market`、`language`、`product_id` 和可选 `therapeutic_area`
- `content`
- 内容分段（可选）
- 结构化业务标签（可选）
- 规则包选择与版本
- 数据分类、保留策略与外部关联 ID（可选）

外部关联 ID 仅用于调用方追踪，不参与策略判断。所有上下文必须带租户边界，
缓存、检索、审计和运行文件均按租户隔离。

### 4.3 防止内容丢失

脱敏只能替换被识别实体的精确片段。实体解析在脱敏前完成；规则评估必须使用
保留结构与替换标记的安全文本。需要同时验证：

- 敏感信息召回率。
- 原始内容与脱敏内容之间的非实体片段保真度。
- 脱敏后规则命中不下降。

## 5. 共享规则库

### 5.1 规则分类

初始规则包至少覆盖：

| 分类 | 示例风险 |
| --- | --- |
| 不良事件 | 明确或隐含的安全事件、严重性、随访信息 |
| 患者隐私 | 姓名、联系方式、病历号、健康信息、可复原组合 |
| 商业行为 | 贿赂、不当利益、回扣、款待、利益冲突 |
| 处方数据 | 患者级处方、处方针级可识别统计 |
| 超适应症 | 未批准适应症、人群、剂量、途径或联合用药 |
| 证据完整性 | 声称缺少、冲突或过期证据 |
| 提示注入 | 绕过规则、窃取系统提示、伪造权限 |
| 生成安全 | 泄露上下文、给出危险医疗建议、隐藏真实风险 |
| 自定义规则 | 企业、市场或治疗领域附加要求 |

### 5.2 规则结构

规则需要包含：

```text
rule_id
version
title
description
category
severity
decision
scope
conditions
span_locator
allow_save
allow_generate
allow_publish
notification_message
remediation_guidance
required_roles
sla
suppression_policy
evidence_requirements
test_cases
```

字段行为：

- `scope`：租户、市场、语言、产品、治疗领域、内容类型、入口。
- `conditions`：确定性模式、结构化字段约束、证据检查或批准的候选提取器。
- `span_locator`：返回 `char:start-end` 位置；多个命中返回多个片段。
- `allow_save`：是否允许保存人工内容。
- `allow_generate`：该规则是否允许请求进入模型生成。
- `allow_publish`：模型输出是否可发布。
- `notification_message`：面向作者或复核者的通知。
- `remediation_guidance`：具体整改方向，不承诺删掉片段即可解决问题。
- `suppression_policy`：低置信候选、重复命中或已批准例外是否可降级；红线
  规则不允许静默抑制。
- `evidence_requirements`：需要药物标签、批准材料或政策依据时的证据条件。

### 5.3 规则版本与发布

规则包采用草稿、测试、发布和回滚流程。每次检查记录实际生效的规则包版本和
规则版本。历史案例保持原判定；重新评估必须生成新评估版本，不能覆盖原记录。

发布前至少执行：

- 规则单元测试。
- 基准集回归测试。
- 危险放行与过度阻断检查。
- 输入和输出两个入口的适用性检查。
- 片段位置与原文映射检查。

### 5.4 规则调试与批量评估

规则工作台提供：

- 单条文本即时调试。
- 预期命中、不应命中和片段位置断言。
- 批量文本文件导入与结构化结果导出。
- 规则版本间差异。
- 误报、漏报、危险放行分级统计。
- 人工确认结果回填为后续回归样本。

批量评估默认脱敏并限制文件大小；导入文件不得执行脚本、公式或外部引用。

## 6. 内容合规检查

### 6.1 检查流程

1. 验证身份、租户、权限、内容和规则包。
2. 解析语言、内容类型和结构化标签。
3. 识别并脱敏敏感实体，保留原文位置映射。
4. 运行适用规则和允许的候选提取器。
5. 由确定性引擎计算严重度、处置、角色和 SLA。
6. 返回命中片段、规则依据、整改建议和后续操作。
7. 将提交检查写入案例、审计和工作流记录。

检查分三类时机：

- 编辑中检查：仅返回快速提示，不创建最终案例。
- 提交前检查：创建检查记录，可要求补充或复核。
- 保存后检查：针对已保存版本生成可追踪结果，并通知内容所有者。

编辑中检查不得显示“无问题”或“合规通过”；它只能提示已发现的风险和覆盖
范围有限。

### 6.2 片段结果

每个finding返回：

```text
finding_id
rule_id
rule_version
category
severity
decision
reason
spans[]
matched_terms[]
notification_message
remediation_guidance
required_roles[]
allow_save
next_action
```

`spans` 每项包含对当前文本版本的 `start`、`end` 和可选 `quote_hash`。服务端
按 Unicode 字符偏移计算位置，前端高亮严格使用服务端位置。若内容已修改导致
位置失效，返回 `stale`，要求重新检查，不猜测新位置。

规则必须返回真实原文位置，不能通过搜索相似文本伪造高亮。以下情况视为定位
不可用：

- 命中来自证据比较、字段冲突或模型候选，无法可靠对应原文。
- 同一短语多次出现，无法确定是哪一次。
- 脱敏改写改变了长度，但位置映射尚未验证。

定位不可用时仍可保留 finding，但 `spans` 为空；若该规则的发布要求必须有
片段证据，则检查进入 `human_review` 或 `MANUAL_DEGRADED`，不能以空片段
假装证据完整。

界面明确显示：“高亮片段是风险证据，不一定是完整原因。删除词语可能不改变
事实、意图或证据问题。”

### 6.3 真实渠道更新

已保存内容被修改时生成新版本并重新检查。上一版本的真实渠道状态不回写为
“已通过”。渠道处理结果使用中性状态：

- 未处理
- 处理中
- 需补充
- 待复核
- 已阻断
- 已关闭

## 7. AI 对话合规防护

### 7.1 三阶段链路

```text
User input
   │
   ▼
[1] Input guard
   ├─ blocked ──────────────► safe response, no model call
   └─ allowed / review risk
            │
            ▼
[2] Constrained generation
   ├─ applicable rules + safe context + output contract
   └─ model candidate response
            │
            ▼
[3] Output guard
   ├─ blocked ──────────────► withdraw / replace with safe notice
   ├─ needs_info / review ──► hold or route
   └─ allow ────────────────► publish
```

三阶段共享同一规则集，但规则可以用 `scope.entrypoint` 限制只作用于输入或输出。

### 7.2 输入检查

输入检查覆盖：

- 提示注入和指令覆盖。
- 索取个人或患者数据。
- 要求规避合规规则或伪造审核。
- 要求生成超适应症推广、贿赂安排或患者级处方信息。
- 明确不良反应或安全事件，需要转专业流程或请求最小必要补充。

输入为 `blocked` 时，不调用外部或本地生成模型。返回安全说明、适用的整改
方向和非敏感的人工支持入口。

通过输入检查时，服务端创建一个有期限的对话防护会话，并记录：

- `conversation_id`
- 租户和用户
- 已检查输入的哈希与安全文本版本
- 输入检查结果和规则版本
- 允许生成的约束摘要
- 失效时间

生成接口只接受有效的防护会话，不接受客户端在检查后替换的新提示词。过期、
跨租户、已被阻断或规则版本已变化时，要求重新检查。实现不得把“客户端持有
一个成功标志”当作输入检查通过的证明。

### 7.3 生成约束

通过输入检查后，生成请求包含：

- 已批准的系统安全约束。
- 当前请求适用的规则摘要。
- 最小必要的产品与证据上下文。
- 输出结构要求。
- 不能披露内部规则、令牌映射或系统提示的指令。

规则摘要不能代替输出检查。生成时的指令只是降低风险，最终发布仍由输出检查
决定。

### 7.4 输出检查与撤销

输出在发布前执行与输入相同的规则引擎，并增加：

- 上下文泄露检查。
- 高风险医疗建议检查。
- 证据一致性检查。
- 不安全承诺或误导性确定性检查。

`blocked` 输出不得原样返回。服务端执行以下之一：

1. 若已配置安全改写器且改写结果通过检查，返回改写版本。
2. 否则返回通用安全提示，不显示被阻断的生成正文。

若输出检查组件超时或异常：

- 高风险请求进入 `FAILED_SAFE` 或 `MANUAL_DEGRADED`。
- 响应不得发布未检查文本。
- 审计记录检查状态、规则版本和错误类别。

输出检查与生成在同一服务端会话中完成。浏览器不能单独声明输出“已通过”，
也不能把未经检查的模型响应标记为可发布。

默认采用完整输出缓冲后再检查，不向浏览器逐 token 流式发布。未来若增加流式
体验，只能在发布前经过增量检查闸门，并具备超时阻断、敏感片段遮罩和整段撤销
能力；未实现这些条件时不得开放流式通道。

### 7.5 审计与敏感正文

审计默认记录：

- 请求 ID、租户、时间、入口、内容类型与规则版本。
- 输入和输出的检查结论、命中规则、片段位置与安全哈希。
- 模型配置标识、调用耗时和失败类别。
- 是否调用模型、是否撤销输出、是否进入人工复核。

默认不记录：

- 完整原始输入。
- 完整模型输出。
- 脱敏前的敏感实体。
- 系统提示和令牌映射。

如企业明确启用受控正文保留，则必须按租户设置保留期限、访问角色、加密和
删除流程，并在审计中记录访问。

删除受控正文时写入不包含正文的 tombstone，保留记录 ID、原内容哈希、删除
原因和时间。这样既执行保留策略，又能继续验证审计链。正文删除与审计链清理
必须分开授权和记录。

## 8. 人工复核与反馈闭环

复核工作台支持：

- 查看安全文本、片段位置、规则依据和证据。
- 同意、要求补充、阻断或升级。
- 记录理由和适用的电子签名。
- 将模型候选与规则命中分开显示。
- 对规则提出误报或漏报反馈。
- 对输出检查失败进行恢复或重新生成。

复核结果进入规则调优队列。更新规则后必须通过回归评估；不能直接用单个案例
覆盖已发布规则。申诉创建新任务，不会自动解除阻断。

## 9. 通用连接器契约

连接器是可选边界，不包含厂商 SDK 或固定业务对象。初始契约包括：

### 9.1 Content Source

- 读取或接收待检查内容。
- 返回外部记录 ID、版本、内容类型、语言、市场和内容正文。
- 支持幂等键和版本冲突检测。

### 9.2 Safety Intake

- 接收经过最小化处理的安全事件候选。
- 返回接收确认和外部跟踪 ID。
- 失败时保留本地待处理记录，并触发人工路径。
- 连接器不可用不能删除风险信号。

### 9.3 Review Export

- 导出待复核任务、决策、理由和审计引用。
- 写入必须显式启用并通过权限检查。
- 重试使用幂等键；永久失败进入死信状态供人工处理。

所有连接器使用通用 HTTP JSON 或实现方自定义传输，并在注册表中声明能力、
数据分类、允许的动作和健康状态。仓库只提供契约、参考实现和测试替身。

## 10. API 边界

保留现有案例、复核、规则、审计和健康检查 API 的可用部分，新增统一的入口
语义。建议公共接口：

```text
POST /api/checks/precheck
POST /api/checks
GET  /api/checks/{check_id}
POST /api/conversations/guard-input
POST /api/conversations/{conversation_id}/generate
GET  /api/conversations/{conversation_id}
GET  /api/rules
POST /api/rules/test
POST /api/rules/evaluate
POST /api/rules/publish
POST /api/rules/rollback
GET  /api/reviews
POST /api/reviews/{task_id}/decision
GET  /api/audit-trail
GET  /api/audit-trail/verify
```

`generate` 在返回前完成输出检查。发布正文要么已通过检查，要么由服务端提供的
安全替换内容代替；端点不返回被阻断的原始生成结果。

兼容策略：

- 现有 `/api/cases/*` 可以保留为内部兼容路由，逐步映射到通用检查语义。
- 旧字段通过 Pydantic 校验别名读取，响应同时提供新字段；文档只描述新字段。
- 删除固定厂商适配器、固定渠道示例和对应测试。
- 迁移期间不改变既有案例的安全语义和审计链验证方式。

## 12. 安全与失败处理

### 12.1 信任边界

- 浏览器输入不可信。
- 模型输出不可信。
- 连接器响应不可信。
- 规则文件和导入文件需要校验。
- 前端授权提示不是授权控制。

### 12.2 Fail-safe

| 情况 | 行为 |
| --- | --- |
| 规则引擎异常 | 不给出 `allow`；进入安全失败或人工复核 |
| 输入检查异常 | 不调用生成模型 |
| 输出检查异常 | 撤销输出；返回安全提示 |
| 脱敏失败 | 阻断外发与生成 |
| 审计写入失败 | 释放类操作失败；不宣称成功 |
| 安全接收连接器失败 | 保留本地记录并进入人工路径 |
| 规则版本缺失 | 拒绝检查或进入人工复核 |

### 12.3 数据保护

- 租户级隔离所有案例、规则、复核、导出和运行文件。
- 敏感信息在模型调用前脱敏。
- 日志不记录正文和令牌映射。
- 文件上传限制类型、大小和解析深度。
- 规则导入禁止可执行内容。
- 审计记录使用哈希链验证篡改。
- 删除和保留按租户策略执行，并在审计中记录。
- AI 会话默认只保存安全文本和哈希，并设置独立于案例的短保留期限。

## 16. 完成标准

满足以下条件才算完成：

1. 独立模式无需任何特定厂商服务即可启动并完成两类检查。
2. 内容检查支持共享规则、片段证据、保存行为、整改建议和人工复核。
3. AI 对话防护实现输入阻断、生成约束、输出撤销和失败安全。

5. 审计默认不保存敏感正文，并能验证哈希链。
6. 中英文界面和文档均使用通用医药行业术语。
7. 仓库中不存在特定厂商品牌、产品对象、固定工作流依赖或相关适配器。
8. 单元、集成、回归和安全测试全部通过；文档中的测试数据来自本次执行。
9. 变更提交并推送到用户指定的 GitHub 仓库。

## 17. 方案选择记录

考虑过三种路线：

1. **统一独立合规网关**：一个服务和一个双语界面，共享规则、复核与审计。
2. **双产品工作区**：两类入口拥有独立前后端边界，维护成本更高。
3. **API 优先加参考界面**：易嵌入企业系统，但独立规则管理与复核体验较弱。

用户选择统一独立合规网关。该路线在核心控制和治理能力上保持一致，同时通过
调用入口隔离“检查静态内容”和“保护 AI 对话”的用户体验。
