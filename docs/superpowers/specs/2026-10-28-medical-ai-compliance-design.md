# 医药行业独立 AI 合规检查网关设计

日期：2026-10-28

状态：已批准（2026-10-28）

## 1. 背景与目标

现有核心已经具备确定性策略判定、模型候选约束、实体消解与打码、提示注入检测、
人工复核、失败安全、哈希链审计和中英文界面。字段与工作区仍带有单一定向工作流
假设，需要改造成可以独立部署的医疗内容与 AI 对话合规网关。

### 1.1 目标

1. 提供内容检查入口，在保存、发送或发布前检查任意医疗行业文本。
2. 提供 AI 对话防护入口，在输入、生成和输出三个阶段约束模型链路。
3. 两个入口共用规则库、策略引擎、finding Schema、复核队列与审计链。
4. 返回字符片段、规则依据、严重度、允许动作、整改方向和复核角色。
5. 允许按租户、市场、语言、产品、治疗领域、内容类型和入口配置规则。
6. 保留失败关闭、模型只提出候选、人工权限和审计发布前写入。
7. 独立模式无需客户系统、厂商 SDK、外部数据库、消息队列或在线模型即可运行。
8. 文档、界面、配置和测试不再包含固定厂商、固定渠道或单一客户工作流。

### 1.2 非目标

1. 不构建通用大模型、模型托管平台或企业知识库。
2. 不替代医学、法务、药物警戒或监管部门的最终判断。
3. 不声称完成 GxP/CSV、MLR、药物警戒或目标市场法规验证。
4. 不内置单一组织的审批层级、岗位编码或外部数据对象。
5. 默认不保存 AI 原文、完整生成结果、敏感实体或 token 映射。
6. 不要求生产必选数据库、消息队列、身份提供方或云模型。

### 1.3 反目标

1. 不允许模型决定严重度、处置、复核路由或发布权限。
2. 不允许把“没有命中规则”表述为法规批准。
3. 不允许输出检查失败时展示或发布未经检查的模型结果。
4. 不允许删除高亮片段就宣称风险已经解决。
5. 不允许无版本记录地改变另一入口的历史判定。

## 2. 产品原则

### 2.1 共享核心，两个入口

```text
                  Shared rule registry and policy
                     versions / scope / findings
                              │
              ┌───────────────┴────────────────┐
              │                                │
    Content check                    AI conversation guard
    saved or draft text              input / generation / output
              │                                │
              └───────────────┬────────────────┘
                              │
              Review tasks · case records · audit chain
```

服务端是最终判定唯一有权方。模型和规则抽取器可以提出候选 finding 或回复；严重度、
最终处置、发布动作、复核要求和审计动作由确定性代码计算。

### 2.2 独立部署优先

| 模式 | 必需组件 | 外部集成 | 用途 |
| --- | --- | --- | --- |
| Standalone | 本服务、本地 JSON/JSONL | 无 | 本地演示、测试和单机试用 |
| Integrated | 本服务、企业身份和持久化存储 | 仅启用的连接器 | 企业接入 |
| Controlled | Integrated 加部署加固 | 明确清单和权限边界 | 受控生产环境 |

Standalone 必须支持内容检查、AI 防护、规则生命周期、复核、审计与导出。缺少
连接器不能阻断核心检查能力。

### 2.3 处置语义

| 处置 | 含义 | 默认行为 |
| --- | --- | --- |
| `allow` | 当前规则未发现需要保持的问题 | 允许继续，但不保证合法 |
| `needs_info` | 缺少完成判断所需信息或证据 | 请求补充，不宣称通过 |
| `human_review` | 发现高风险或需要专业判断 | 进入人工复核 |
| `blocked` | 命中红线或无法安全检查 | 禁止保存、生成或发布 |

`refused` 保留为授权或不可处理请求的内部终态。`MANUAL_DEGRADED`、
`FAILED_RETRYABLE` 与 `FAILED_SAFE` 保持可见，任何失败状态都不能产生可发布的
`ALLOWED` 结果。

## 3. 用户与角色

角色使用中性职能，不绑定固定岗位名称：

| 角色 | 职责 |
| --- | --- |
| `author` | 编写内容或发起 AI 对话 |
| `submitter` | 提交检查并补充所需信息 |
| `reviewer` | 完成常规合规复核 |
| `safety_reviewer` | 评估不良事件和患者安全信号 |
| `medical_reviewer` | 评估医学信息与超适应症风险 |
| `legal_reviewer` | 评估法律和商业行为风险 |
| `compliance_admin` | 管理范围、规则和合规配置 |
| `architect` | 查看和起草模型档案与任务路由，不能发布 |
| `auditor` | 只读查看审计证据与质量状态 |
| `admin` | 管理部署、用户、身份和保留策略 |

规则要求角色集合而非单一人员。演示界面提供 `author`、`reviewer`、`auditor`、
`architect` 四个角色；服务端权限矩阵可以支持更广的专业路由。服务端独立检查权限，
前端隐藏控件不构成授权。

## 4. 内容模型

### 4.1 通用类型

| 类型 | 用途 |
| --- | --- |
| `customer_interaction_note` | 客户互动记录或会议纪要 |
| `medical_information_request` | 医学信息咨询与答复 |
| `medical_field_note` | 医学事务记录 |
| `promotional_content` | 推广、培训或数字内容 |
| `ai_conversation` | AI 对话输入或输出 |
| `other` | 企业自定义内容 |

调用方可以提供 `content_subtype`。内容类型影响默认规则作用域、留存和复核角色，
不硬编码特定外部系统对象。

### 4.2 检查上下文

每次检查包含：

- 必填租户、市场和语言。
- 内容类型与可选细分类型。
- 可选产品与治疗领域。
- 正文或结构化内容分段。
- 可选结构化业务字段。
- 可选规则版本、留存策略、外部关联 id 和客户端内容版本。

外部关联 id 只用于调用方追踪，不参与策略判断。缓存、检索、会话、审计和运行
文件都按租户隔离。

### 4.3 保真打码

实体消解先于打码。打码只替换识别出的实体片段，规则读取保留叙述结构的安全文本。
系统同时度量：

- 敏感信息召回率。
- 非实体原文的源保真度。
- 打码后的规则命中变化。
- 错误合并率和共指准确率。

身份合并不确定时进入 `needs_info`，不能静默合并两个可能的人。

## 5. 共享规则库

### 5.1 风险范围

默认策略包覆盖：

| 类别 | 风险 |
| --- | --- |
| 不良事件 | 潜在或严重安全事件、随访信息 |
| 隐私 | 联系方式、身份号码、健康信息、可复原组合 |
| 商业行为 | 贿赂、不当利益、不当诱导、利益冲突 |
| 超适应症 | 未批准适应症、人群、剂量、途径或联合用药 |
| 证据 | 缺失、冲突、过期、跨版本 |
| 提示注入 | 指令覆盖、权限伪造、提示泄露 |
| 生成安全 | 上下文泄露、危险建议、隐藏真实风险 |
| 格式与质量 | 片段、术语、必要上下文和保留提醒 |

### 5.2 规则字段

```text
rule_id
version
title
category
severity
decision
scope
conditions
allow_save
allow_generate
allow_publish
notification_message
remediation_guidance
required_roles
sla
evidence_requirements
test_cases
```

`scope` 包含市场、语言、产品、治疗领域、内容类型和入口。入口至少为 `content`、
`input` 和 `output`。规则适用域不匹配时不能借用另一个入口的历史结论。

`conditions` 可以是确定性模式、字段比较、证据约束或经校验的候选提取器。模型候选
必须通过 Schema 校验，不能扩展工具、路由或权限集合。

### 5.3 生命周期

规则包以不可变版本完成：

1. 起草新版本并记录差异。
2. 运行单例测试，包括预期命中、不应命中和片段位置。
3. 运行批量或黄金集回归。
4. 检查危险放行、证据缺口、权限和双端适用性。
5. 发布快照。
6. 必要时回滚到先前已发布快照。

每次检查记录实际策略和规则版本。发布和回滚需要管理员权限并写入审计。历史结果
保持原版本；重新评估生成新版本，不能覆盖原记录。

## 6. 内容合规检查

### 6.1 路径

1. 校验会话、租户、权限、请求 Schema 和规则版本。
2. 解析内容类型、语言、产品、市场和结构化字段。
3. 完成实体消解与选择性打码。
4. 检索当前租户和市场可用的版本化证据。
5. 运行确定性规则与允许的候选抽取。
6. 由策略引擎计算处置、严重度、动作与复核路由。
7. 写入安全审计后返回结果。

`POST /api/checks/precheck` 用于编辑期间快速反馈。它不创建案例，不保存提交正文，
不调用模型。它只显示当前规则覆盖范围内发现的风险，不能显示“法规通过”。

`POST /api/checks` 保存版本化结果。文本修改后必须重新检查，不能把旧结果应用到
新版本。

### 6.2 Finding 与片段

Finding 包含规则 id、规则版本、类别、严重度、处置、原因、匹配词、片段、允许动作、
通知和整改方向。片段使用相对于本次提交版本的 Unicode 字符偏移。

规则无法可靠定位时保留 finding 并让片段为空。系统不会搜索相似文本并把猜测位置
当作证据。若规则要求片段而定位不可用，检查进入复核或安全失败。

界面明确说明高亮是风险证据的一部分。删除词语可能改变不了事实、意图或证据问题。

### 6.3 证据与超适应症

产品标签在接入阶段结构化为版本化事实。模型可以提出适应症、人群、治疗线数、剂量、
途径和联合用药候选；服务端逐字段比较。

证据检索按租户、市场、产品、语言、状态、有效期和访问范围过滤。缺失、过期或跨
版本证据产生显式 finding，不能静默放行。

## 7. AI 对话合规防护

### 7.1 三阶段

```text
Input
  ├─ blocked: return safe notice; create no session; call no model
  └─ allowed or held: create server-bound session
                         │
Generation               ▼
  ├─ verify actor, tenant, prompt hash, rule version, expiry
  ├─ send bounded safe input and applicable constraints
  └─ buffer complete candidate
                         │
Output                   ▼
  ├─ blocked or failed: withdraw model text
  └─ allow: increment generation and release safe text
```

### 7.2 输入检查

输入检查覆盖提示注入、指令覆盖、索取敏感数据、规避规则、伪造审核、请求超适应症
推广、商业利益输送和不安全医疗建议。

`blocked` 输入不调用模型。安全或可复核输入建立短期服务端会话，记录：

- `conversation_id`。
- 操作者和租户。
- 检查原文 SHA-256。
- 安全输入和服务端内容版本。
- 输入处置和规则版本。
- 允许生成的约束。
- 失效时间，默认 15 分钟。

浏览器不能用一个成功标志代替输入检查。提示词改变返回
`conversation_prompt_mismatch`；规则版本改变返回
`conversation_requires_recheck`；过期或关闭返回 `conversation_expired`。

### 7.3 生成

生成接口只接受有效会话与同一份已检查输入。请求包含系统安全约束、适用规则摘要、
最小产品与证据上下文和输出结构要求。内部提示、token 映射和完整规则文本不传给
调用方。

规则摘要降低风险，最终发布仍由输出检查决定。模型不能通过回复修改路由、工具集合、
决定、严重度或角色。

### 7.4 输出检查

完整候选缓冲后进入共享策略路径，并叠加输出入口规则。输出检查至少覆盖：

- 上下文泄露和内部提示泄露。
- 高风险或缺少证据的医疗建议。
- 超适应症、商业诱导和不安全承诺。
- 标签事实冲突与敏感信息。

只有总处置为 `allow` 且所有 finding 都允许发布时才展示正文。阻断时撤回候选，
返回安全说明与 finding；失败时返回 `failed_safe`，状态码为 503。不得回显被阻断
的模型正文。

### 7.5 审计与敏感正文

审计默认记录请求 id、操作者、租户、入口、时间、内容类型、规则版本、安全内容哈希、
处置、finding 引用、模型档案、时延、输出检查和撤回状态。

默认不记录原始输入、完整模型输出、敏感实体值、token 映射、系统提示或凭据。
如企业显式启用受控正文留存，需要租户级期限、角色、加密与删除流程，并在审计中
记录访问。删除正文时写入不包含正文的墓碑记录，保持哈希链可验证。

## 8. 人工复核与反馈

复核工作台支持：

- 查看安全文本、片段、规则、证据和内容版本。
- 同意、要求补充、阻断或升级，并记录理由。
- 使用与审核内容绑定的签名表现形式。
- 区分模型候选与确定性规则命中。
- 对误报、漏报和输出失败提出反馈。
- 通过申诉创建新任务；申诉不会自动解除阻断。

S0 与 S1 不能自我批准。候选用例必须由另一名人员确认后才能进入回归集。规则更新
必须通过完整测试和评估，不能由单个案例覆盖已发布规则。

## 9. 通用连接器

连接器是可选边界，不包含厂商 SDK 或固定业务对象。

### 9.1 内容源

返回外部记录 id、当前版本、权威正文、内容类型、租户、市场和更新时间。事件载荷
只作为通知；服务端按 id 与版本回读权威记录。过期版本返回显式冲突。

### 9.2 安全信号接入

接收经过最小化的安全候选，返回回执和外部跟踪 id。瞬时失败保留本地待处理记录，
用相同幂等键重试。连接器不会替人作安全决定或自动提交法规报告。

### 9.3 复核导出

导出复核任务、决定、理由和审计引用。默认关闭，启用和写入都需要权限。重试使用
幂等键，永久失败进入可见死信状态。

每个连接器声明能力、数据类别、允许动作、版本行为和健康状态。仓库提供内存参考
实现和测试替身，不声称某个外部系统已经配置或验证。

## 10. API 与前端

### 10.1 API 边界

```text
POST /api/checks/precheck
POST /api/checks
GET  /api/checks/{check_id}

POST /api/conversations/guard-input
GET  /api/conversations/{conversation_id}
POST /api/conversations/{conversation_id}/generate

GET  /api/rules
GET  /api/rules/diff
POST /api/rules/test
POST /api/rules/evaluate
POST /api/rules/publish
POST /api/rules/rollback

GET  /api/reviews
POST /api/reviews/{task_id}/decision

GET  /api/audit-trail
GET  /api/audit-trail/verify
```

现有案例路由作为兼容和内部工作流保留，文档以共享检查 API 为主。删除固定厂商
适配器及其耦合测试。兼容层不得改变审计语义或放宽发布权限。

### 10.2 前端信息架构

七个工作区：

1. `overview` — 上下文、状态和两个入口。
2. `content_check` — 任意内容检查。
3. `conversation_guard` — 输入、生成和输出状态。
4. `reviews` — 复核任务、决定与签名。
5. `rules` — 规则版本、测试、评估、发布和回滚。
6. `quality_audit` — 审计链、监督指标、回归候选、连接器和事件。
7. `settings` — 模型档案和任务路由。

界面支持简体中文与英文。语言切换保留草稿和上下文；结果显示易读文案与原始代码；
片段与文本版本绑定；AI 对话区分输入阻断、生成中、输出撤回和安全放行；阻断时
提供原因与下一步，不展示内部提示或敏感规则。

## 11. 安全与失败处理

### 11.1 信任边界

- 客户端输入不可信。
- 模型候选不可信。
- 连接器响应和导入文件不可信。
- 前端能力显示不是授权控制。

### 11.2 失败关闭

| 情况 | 行为 |
| --- | --- |
| 规则引擎异常 | 不给 `allow`；进入安全失败或人工复核 |
| 输入检查异常 | 不调用模型 |
| 打码失败 | 不向模型外发原文 |
| 生成失败或格式异常 | 进入 `MANUAL_DEGRADED` 或 `FAILED_SAFE` |
| 输出检查异常 | 撤回输出，不发布正文 |
| 审计写入失败 | 发布失败 |
| 规则版本缺失或变化 | 拒绝或要求重新检查 |
| 连接器失败 | 保留本地记录并进入人工路径 |

### 11.3 数据保护

- 模型访问前按识别片段打码。
- 日志和默认审计载荷不保存正文、敏感实体或 token 映射。
- 上传限制类型、大小和解析深度。
- 规则导入禁止可执行内容。
- 凭据只通过环境变量或 gitignored 密钥文件引用。
- 已发布规则和模型配置不可变并带版本。
- 审计使用哈希链，校验端点报告第一个不可信位置。

## 12. 测试与完成标准

测试包括单元、契约、集成、安全、评估与文档契约：

- 两个入口共享 finding 和判定语义。
- 输入阻断时零模型调用。
- 会话绑定操作者、租户、原文哈希、规则版本和有效期。
- 提示词和规则版本变化要求重新检查。
- 输出阻断或失败时零不安全正文发布。
- 审计失败时发布失败。
- 权限、复核路由、打码和源保真满足门禁。
- 中英文文档、API、工作区和状态代码一致。
- 仓库不含固定厂商、固定渠道或旧业务工作流耦合。

完成判断依赖实际执行结果，文档不沿用历史测试数字。黄金集至少报告匹配数、总数、
危险放行数、15 项发布门禁和端到端审计校验结果。

满足以下条件才算实现完成：

1. 独立模式无需特定厂商服务即可启动并完成两个入口。
2. 内容检查支持共享规则、片段、动作、整改和复核。
3. AI 链路实现输入阻断、生成约束、输出撤回和失败关闭。
4. 规则可测试、批量评估、发布、回滚并保持历史版本。
5. 模型档案和任务路由可校验、测试、发布和回滚。
6. 审计默认不含敏感正文，哈希链可验证，审计失败阻止发布。
7. 中英文界面、文档和测试使用通用医疗术语。
8. 完整测试、黄金集、发布门禁和端到端验证通过。
9. 变更提交、合并并推送到指定仓库。

本规格状态保持“已批准”。只有上述条件全部由本次验证证据确认后，才能报告实现
完成。

## 13. 方案选择

考虑过三条路线：

1. 统一独立网关：共享规则、复核、审计与发布门禁。
2. 两个独立产品：两个前后端栈，维护和规则一致性成本更高。
3. API 优先加轻量界面：便于嵌入，但独立规则治理与复核体验较弱。

选择统一独立网关。两类入口在服务和数据模型中共享控制面，在用户体验和规则作用域
上保持明确边界。
