# 安全与风险

[English](../security-and-risk.md) · **简体中文**

信任边界、AI 风险登记册，以及缓解每项风险的具体控制措施。此处列出的每项控制均已实现，并有测试覆盖。

## 1. 信任边界

四条边界，按请求穿越它们的顺序排列。

| 边界 | 规则 | 由什么强制 |
| --- | --- | --- |
| **客户端 → 服务端** | 客户端输入是数据，永远不是事实或权限。结构化字段进入 `claimed_fields`；服务端推导 `resolved_fields` | `claim_discrepancy`（CN-020）；保留键被拒绝 |
| **服务端 → 模型** | 标识符在跨越进程边界前已打码。模型接收 token 与结构化事实，绝不接收真实姓名或说明书原文 | `security/pii_gateway.py`、实体消解、数据分级路由 |
| **模型 → 决定** | 模型输出是候选。它无法设置决定、严重度、批准状态、路由或工具权限 | `agents/extractor.py` → Schema 校验 → `policy/engine.py` |
| **服务端 → 外部系统** | 内容从源系统回读；写入需审批令牌加幂等键 | `integrations/` 适配器；不存在通用管理工具 |

第三条边界最关键，而它是**结构性的而非靠提示词约定**：从模型输出到最终结论之间不存在代码路径。

## 3. 打码：两个失败方向

打码不足会泄露标识符。打码过度会删掉叙述——而后者才是**掩盖风险**的失败模式，因为它可能在安全规则读到文本之前就剥掉不良事件关键词。

两者都是发布门禁，下限均为 1.0：**打码召回率**（所有必须打码的内容无一漏过）与**源保真度**（所有非标识符内容无一受损）。两者都不是可调目标。**没有一个可接受的"未打码姓名数量"，也没有一个可接受的"被删除症状数量"。**

实体消解补充第三项度量：**错误合并率必须低于 0.01**，比它旁边 0.95 的共指准确率目标更严——因为把两位临床医生合并，等于把一个人的意见归到另一个人名下。

## 4. 注入防御

扫描在模型调用**之前**执行，因此恶意指令根本到不了模型。命中即 CN-005：S0、`blocked`、路由至安全、SLA 立即。

试图篡改工具或路由的行为会被**记录并路由，绝不执行**。保留表单键无法从入参设置。红队用例（G-37..G-42）作为永不用于调优的留出集被隔离，并且若任何已知注入以 `allow` 结束，发布门禁即失败。

注入同时也演示了下面的队列范围规则：它保持被拦截，但不会塞满医学审核人的队列。

## 5. 审核队列范围

专业审核队列只列出医学或合规审核人**能够处理**的 finding。平台安全类工作——提示词注入、权限失败、不可逆写入拦截——路由至安全/管理员，并从默认队列中排除。医学审核人对一次注入尝试无从下手。

**从队列中排除某一行，绝不等于压制该 finding。** 决定保持 `blocked`，finding 保留在案例和代表的结果里，审核任务照样创建并照样写入账本，而 `GET /api/reviews?scope=all` 会返回这些安全任务。响应还会报告 `business_count` 与 `technical_count`，因此即使未列出，技术工作的存在依然可见。四项测试锁定这一点，其中包括"注入案例在过滤后仍处于拦截状态"。

## 6. 药物警戒评估

当叙述包含不良反应术语时，案例会携带针对四项最低标准的 ICSR 评估：

| 标准 | 由什么满足 |
| --- | --- |
| 可识别的患者 | 一个患者术语，或一个 token 化的患者实体 |
| 可识别的报告人 | 一个报告人术语，或提交的业务代表 |
| 可疑药品 | 案例上下文中的产品 |
| 可疑不良反应 | 叙述中的反应术语 |

这些标准询问的是可识别方**是否存在**，而绝非系统是否持有其标识符——评估运行在 token 化后的叙述上，因此与打码不变量完全兼容。

上报时限，以企业首次获知时间（而非分诊时间）为起点：

| 严重性 | 时限 |
| --- | --- |
| 致死、危及生命 | 7 个日历日，快速上报 |
| 其他严重（住院、致残、先天异常） | 15 个日历日，快速上报 |
| 非严重 | 汇总上报，无快速时限 |

**不完整的 ICSR 永远不会压制安全信号。** 缺失的标准会变成一项跟进任务，案例依然路由至药物警戒。这是该模块中最重要的行为，并由测试锁定。当策略引擎标记了安全 finding 但 ICSR 判读为非安全相关时，界面还会呈现 `assessment_conflict`——这种分歧必须让审核人看到，而不是静默处理。

这是分诊辅助工具，不是安全数据库，也不构成法规建议。时限惯例随市场与产品生命周期而变。

## 7. 电子签名

每条记录在案的审核决定都携带 Part 11 风格的签名表现形式，包含 11.50 要求的三项要素：签署人打印姓名、签署日期与时间，以及签名的**含义**（批准放行 / 驳回 / 升级 / 退回补充信息）。

签名通过对签署内容的 SHA-256 摘要与决定绑定，因此无法被转移到其他内容上以伪造记录；任何被绑定字段发生变化，校验即失败。

**对强度保持诚实。** 没有身份提供方、没有第二因子、没有证书，因此 `signature_kind` 被记录并显示为 `demo_manifestation`。它演示合规签名的形态，不作任何验证声称。

## 8. 数据完整性（ALCOA+）

质量工作区说明账本如何满足可归属、可读、同步记录、原始、准确，以及完整/一致/持久/可获取。自动化流水线步骤被归属于系统而非某个人，界面会明确写出这一点，而不是暗示存在人工操作者。

接口治理登记册按连接器记录：供应商、接口版本、认证方式、凭据**引用**（绝非数值）、数据驻留、数据分级、验证状态、GxP 相关性、管辖 SOP、留存期与写入能力。每个连接器都报告 `validation_status: not_validated`。

审计轨迹受权限限制，因为它记载了谁做了什么：`field_rep` 与 `msl` 会收到 `403`。

## 9. 双向度量的人工监督

高推翻率是显而易见的告警。而低推翻率同样重要：如果审核人几乎从不表示异议，审核可能已流于形式，而**一个盖橡皮章的审核人在记录上与一个完美无瑕的系统长得一模一样**。因此监督指标在**低于 2%** 时也会告警。

放弃行为出于同样理由被追踪——提示出现，然后整段被删掉。既没有拦截也没有 finding，因此这种失败在安全指标里完全隐形。检出数下降的同时放弃率上升，意味着规则变紧了，而不是风险消失了。

S0 与 S1 不可自我批准，这为上述两者都设了一道结构性底线。

## 10. 密钥管理

凭据从不进入代码仓库。Profile 只持有 `credential_ref`；真实密钥来自 `COMPLIANCE_GUARD_LLM_API_KEY` 或被 gitignore 的 `config/secrets/llm.local.json`。草稿校验会在发布前拒绝明文密钥与字面量 endpoint。日志与审计载荷仅携带摘要、id 与聚合值。Profile 响应把凭据引用脱敏为 `****`。

## 11. 范围与不作声称的事项

这是一个 MVP。它演示这些控制措施的**形态**，以便设计可被评审；它不是经过验证的实现。

- 对 GxP/CSV、PV、MLR 或法规验证**不作任何声称**。
- **未与任何在线** CRM、内容库或安全数据库集成。适配器仅为契约实现，返回 `mock://` 回执并使用内存存储；契约测试通过 monkeypatch socket 层断言零网络调用。
- ICSR 模块是分诊辅助工具，不是安全数据库。
- 签名为 `demo_manifestation`：没有身份提供方，没有第二因子。
- 会话是最小化的本地存储，不是企业级 SSO。
- 每个连接器都报告 `validation_status: not_validated`。
- 全部数据为合成或去标识化数据。没有任何真实患者、医疗专业人士或市场数据。

本文档不构成任何法规建议。
