# 验证

[English](../validation.md) · **简体中文**

系统如何被度量：测试分层、合成黄金集、15 项发布门禁、评测输出与变更控制。
本文记录的结果来自离线 mock 模式运行。

## 1. 测试分层

完整测试套件不需要真实模型供应商：

```text
python -m pytest -q
```

| 层 | 位置 | 主要验证 |
| --- | --- | --- |
| 单元 | `tests/unit/` | 规则 Schema 与优先级、策略处置、路由、状态机、打码、签名、审计、发布、证据比较 |
| 契约 | `tests/contract/` | mock 网关确定性、模型输出 Schema、路由、源适配器、真实适配器失败行为与响应包装，不打开 socket |
| 集成 | `tests/integration/` | 共享检查 API、内容检查生命周期、AI 输入与生成、输出放行、规则、复核、申诉、审计链、鉴权、预检、界面契约 |
| 安全 | `tests/security/` | 注入、模型边界、标识符打码、源保真、实体消解、会话绑定、客户端信任边界、权限绕过、输出撤回 |
| 评估 | `tests/evaluation/` | 黄金集回归、打码与共指分母、超适应症精确率与召回率、15 项发布门禁 |
| 文档 | `tests/test_documentation_contract.py` | 必需的中英文文档、有效链接、共享 API 与工作区事实、规则 id、发布门禁、范围声明与禁用耦合 |

最终测试结果在本文第 3 节记录。文档化构建变化后，不沿用历史测试数量。

## 2. 黄金集

`data/golden_set/cases.jsonl` 包含 44 条确定性合成用例，覆盖七个类别。每一行
记录预期处置、严重度、驱动 finding 类型与必需复核角色，评估器按该基线比对。

| 类别 | 用例 | 覆盖内容 |
| --- | --- | --- |
| `normal_low_risk` | G-01..G-06、G-43 | 已批准标签表述变体；G-43 固定标签剂量冲突基线 |
| `ae_pv` | G-07..G-12 | 不良事件信号与别名，在 S1 转安全与医学复核 |
| `pii_phi` | G-13..G-18 | 联系方式、身份号码、健康信息与安全打码 |
| `off_label_label_version` | G-19..G-24 | 适应症、人群、剂量、途径、治疗线数与证据版本不一致 |
| `commercial_redline` | G-25..G-30、G-44 | 不当诱导与礼品表述；G-44 固定打码碰撞行为 |
| `comparative_claim` | G-31..G-36 | 比较性声明，在 S1 转人工复核 |
| `attack_failure` | G-37..G-42 | 注入在 S0 被阻断，权限拒绝、超时、Schema 失败，以及只记录、绝不执行的工具或路由篡改 |

`entity_resolution_cases.jsonl` 另有 12 条打码与实体消解用例。每条都声明哪些
内容必须打码，以及哪些内容必须逐字保留，因此源保真度是实际度量的比率。

整个黄金集与提示词和规则调优隔离。`attack_failure` 子集还作为永不调优的红队
集隔离。全部内容均为合成或去标识化数据，不包含真实患者、临床人员或市场记录。

## 3. 发布门禁

```text
python tests/evaluation/run_eval.py --mode mock --output artifacts/eval-report.json
```

15 项全部通过才会得到 `release_gate: "pass"`。

| # | 门禁 | 阈值 |
| --- | --- | --- |
| 1 | 危险放行 | 0。**出现一起即报告失败** |
| 2 | 高风险证据缺口 | 每个 S0/S1 finding 都携带证据引用或显式缺口 |
| 3 | 跨版本证据放行 | 0 |
| 4 | 注入被拦截 | 任何注入用例都不得以 `allow` 结束 |
| 5 | 权限拒绝被尊重 | 任何权限拒绝用例都不得被放行 |
| 6 | 受保护角色绕过 | 无相应权限时，发布、回滚或审核决定绝不得成功 |
| 7 | 审计完备性 | 案例完成时不得缺少审计事件与 trace span |
| 8 | 打码召回率 | 1.0 —— 合规底线，不是可调目标 |
| 9 | 源保真度 | 1.0 —— 打码未损坏任何非标识符原文 |
| 10 | 错误合并率 | < 0.01 |
| 11 | 共指准确率 | ≥ 0.95 |
| 12 | 预检 p95 | < 300 ms |
| 13 | 术语表覆盖 | 每条策略规则都有白话措辞 |
| 14 | 提交路径 p95 | < 3 s，并附带 `l2_latency_mode` |
| 15 | 超适应症精确率与召回率 | ≥ 0.90，报告为两个数字 |

部分阈值的非对称性是刻意的：

- **门禁 8 与 9 都要求 1.0。** 只看召回率会允许过度打码，在安全规则读取文本
  前删除症状。
- **门禁 10 比门禁 11 更严。** 把两位临床医生合并，会把一个人的意见归到另一
  个人名下，比未能关联同一个人的两处提及更糟。
- **门禁 15 始终保留精确率与召回率两个数字。** 超适应症是少数类别，一个混合
  准确率可能在检测完全失效时仍然很高。`unresolved_rate` 作为运营信号伴随。
- **门禁 14 必须携带模式标签。** 离线 fixture 时延不是真实供应商保证，两者
  差异很大。

报告记录策略、知识快照、路由、档案、模型、提示词、注册表与代码版本，回归
可以追溯到造成它的改动。

### 已记录的离线结果

最终文档化构建记录 **`1113 项通过、1 项跳过`**。Mock 黄金集匹配
**`44/44`**，危险放行 **`0`**，15 项检查全部通过后报告
`release_gate: pass`。

端到端审计校验返回 `ok: true`。

## 4. 端到端覆盖

集成路径用同一套共享控制验证两个公共入口：

1. 提交干净内容并收到持久化检查。
2. 提交阻断内容，验证发布仍然不可用。
3. 检查安全 AI 输入并收到绑定操作者的会话。
4. 通过会话生成，验证输出经过输出检查。
5. 在检查、生成、复核与发布事件后验证审计哈希链。

这些路径由自动集成测试覆盖。运维人员也可以在运行时通过
`GET /api/audit-trail/verify` 重复审计断言。

## 5. 时延

时延门禁随执行模式一起报告。Mock 模式度量本地工作流开销，不能作为供应商
时延。真实测量必须包含供应商排队、生成、重试与完整输出检查。

预检门禁度量编辑期的确定性反馈。提交路径门禁度量包含审计写入的完整检查路径。
两者都来自评估器的 p95 度量，而不是人工计时印象。

## 6. 受控基线

黄金集和阈值都是版本化测试资产。修改任一项需要：

1. 记录与已确认误报或漏检关联的原因。
2. 候选用例进入黄金集前由另一名人员确认。
3. 重新运行完整 mock 评估与全部测试。
4. 将阈值变化作为单独发布决定进行审核。

安全门禁失败时，应修复规则、检索、打码、鉴权或工作流。把危险放行重新标注为
预期结果，会让指标通过，却移除了它本来要测量的控制。

## 7. 变更控制

每份报告标识策略、证据快照、路由、档案、提示词、注册表与代码版本。发布保留
历史检查实际使用的规则版本，不改写过去的结果。

合并改动之前执行：

```text
python -m pytest -q
python tests/evaluation/run_eval.py --mode mock --output artifacts/eval-report.json
node --check src/compliance_guard/web/app.js
node --check src/compliance_guard/web/i18n.js
git diff --check
```

发布报告必须满足 `matched_cases == total_cases`、
`dangerous_false_allows == 0`、`release_gate == "pass"`。文档契约测试会拒绝
过期的 API、工作区、阶段、范围与双语文事实。
