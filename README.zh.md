# Compliance AI Guard

[English](README.md) · **简体中文**

面向药企一线沟通内容的确定性、失效安全（fail-safe）合规预检系统。它位于拜访记录发出之前的环节，在内容对外释放前判定：可以放行、需要补充信息、须转人工，还是必须拦截。

真正值得说的不是它用了大模型，而是**大模型的权限被压到多低**。模型负责读懂中文自由文本并给出候选结论；决定、严重度、路由、权限全部由服务端代码产出。这个约束就是整套设计的核心，也正因如此，每个案例都可以回放、可以审计、可以向那个必须签字的审核人解释清楚。

```text
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[test]"
LLM_MODE=mock DEMO_MODE=1 PYTHONPATH=src .venv/bin/python -m uvicorn apps.api.main:app --port 8000
```

浏览器打开 http://127.0.0.1:8000。默认完全离线运行——`LLM_MODE=mock` 是默认值，全程零网络调用。也可以用 `LLM_MODE=mock DEMO_MODE=1 python3 run.py` 一条命令自动选端口并打开浏览器。

**范围说明。** 这是一个可运行的 MVP，用于探索在受监管流程中如何约束 AI 层的权限。它对 GxP/CSV、药物警戒（PV）、医学-法务-法规审查（MLR）或法规验证**不作任何声称**，未与任何在线 CRM / 内容库 / 安全数据库集成（适配器仅为契约实现），全部数据为合成数据。那些带法规色彩的功能——ICSR 评估、上报时限、21 CFR Part 11 风格电子签名、ALCOA+ 审计视图——展示的是这些控制措施的**形态**，而非经过验证的实现。本文档不构成任何法规建议。

## 为什么这样设计

三个设计选择承担了主要分量。

**模型提议，服务端决定。** 从模型输出到最终结论之间不存在代码路径。候选结论必须经过 Schema 校验，才进入确定性策略引擎。这不是过度谨慎：在真实模型联调期间，一条只能由模型输出触发、且没有模式匹配的 S0 规则，曾把一次常规审核升级成对完全没有推广意图的内容的拦截。提示词措辞并没有把这些 finding 类型区分开——真正起作用的是策略引擎里的确定性优先级规则。**指令不是控制手段。**

**超适应症由字段比对判定，而不是靠"问模型"。** 一份完整中文说明书有数万字，塞不进请求预算；说明书里无关的叙述（比如临床试验安慰剂组的副作用）会干扰判断；而"我认为这属于超适应症"这种回答根本无法核对。所以分工是：说明书在接入阶段就结构化为版本化的标签事实，模型只抽取七个固定字段（适应症、人群、治疗线数、剂量、给药途径、疗程、联合用药），服务端逐字段比对。出现不一致时，会明确指出是哪个字段没对上。

**打码有两个失败方向，安静的那个更危险。** 打码不足会泄露标识符；打码过度会删掉叙述内容——早期基于正则的实现会替换整个匹配段，于是"赠送礼品给医生"丢掉了承载"礼品"的字符，商业红线规则就此失效。同一机制也可能在安全规则读到文本之前，先抹掉不良事件关键词。现在的做法是：姓名识别锚定在姓氏词典上，只替换姓名本身；实体消解在打码**之前**执行，使同一个人得到同一个 token；两个方向都是发布门禁，阈值都锁定在 1.0。

## 它做什么

**四种决定**——`allow`（放行）、`needs_info`（补信息）、`human_review`（转人工）、`blocked`（拦截）——每个都带严重度（S0 红线至 S3 提示）、证据、白话解释，以及路由到能真正处理它的专业角色。S0 与 S1 永远不允许自我批准。

**21 条策略规则**，覆盖不良事件、严重不良事件、个人与健康信息、超适应症声明、商业红线、比较性声明、提示词注入、证据冲突与缺口、权限失败以及声明不一致。每条规则各自携带严重度、路由和 SLA。

**四个工作区**——代表（提交并查看脱敏结果）、审核（证据、决定、电子签名）、模型策略（起草/测试/发布/回滚）、质量与审计（ALCOA+ 态势、接口治理登记册、审计轨迹）——界面支持简体中文 / English，服务端代码始终以「可读短语 + 原始代码」双重呈现，这样审核人看得懂屏幕，审计人依然能核验轨迹。

**失效安全状态机。** 模型超时、Schema 违规、权限拒绝或未处理异常，都会转入 `MANUAL_DEGRADED`、`FAILED_RETRYABLE` 或 `FAILED_SAFE` 并派单给人。**案例永远不可能从失败状态到达 `ALLOWED`。**

**两层书写时预检**，两层都不调用模型：浏览器端逐键的本地词元提示，以及服务端确定性预检，p95 远在 300 ms 预算之内。两者都不产生记录——草稿不是提交。L0 永远不会说"内容看起来没问题"，因为本地词表支撑不起"未发现问题"这个结论，而虚假的安心会让使用者误以为沉默等于安全。

**防篡改审计轨迹。** 每条记录携带 `sha256(prev_hash + 规范化正文)`；`GET /api/audit-trail/verify` 会报告第一个不可信位置。仅追加（append-only）只是本程序的承诺，而哈希链才是让**他人**的改动可被发现的机制。

**药物警戒分诊**：ICSR 四项最低标准加上报时限（致死/危及生命 7 天，其他严重 15 天，非严重汇总上报），以企业首次获知时间为起点。**不完整的 ICSR 永远不会压制安全信号。**

**双向度量的人工监督。** 人工推翻率**过低**会触发"橡皮章"告警；放弃行为（提示出现后作者直接删掉整段）也被计数。这种失败模式既没有拦截也没有 finding，因此除非专门去看，它在安全指标里是完全隐形的。

**闭环。** 我的记录、审核结果通知、保留父版本的修订，以及在不解除拦截的前提下为人创建工作的申诉通道。

## 验证

```text
python -m pytest -q                                          # 1068 项测试，离线
python tests/evaluation/run_eval.py --mode mock --output artifacts/eval-report.json
```

当前状态：**1068 项通过**，黄金集 **44/44 一致**，危险放行 **0** 起，**15 项发布门禁**全部通过。

在对称会掩盖问题的地方，门禁被刻意设成不对称。打码召回率与源保真度都锁定 1.0。错误合并率（0.01）比共指准确率（0.95）更严，因为把两位临床医生合并成一个人，等于把一个人的意见归到另一个人名下。超适应症报告精确率**和**召回率两个数字，绝不合成单一准确率——多数用例本就不是超适应症，混合评分即使在检测完全失效时也会保持高位。

对接真实模型时，同样 44 条用例仍是 44/44 一致、门禁通过，七次运行的 p95 落在 5.1 秒到 19.7 秒之间。这个跨度是供应商波动，也正是交互路径必须保持确定性、把模型放在其后的原因。详见 [docs/zh/validation.md](docs/zh/validation.md)。

## 真实模型模式

```text
COMPLIANCE_GUARD_LLM_BASE_URL=https://<provider-host> \
COMPLIANCE_GUARD_LLM_API_KEY=<your-key> \
LLM_MODE=live PYTHONPATH=src .venv/bin/python -m uvicorn apps.api.main:app --port 8000
```

支持任何 OpenAI 兼容的 chat-completions 供应商。密钥也可以放在被 gitignore 的 `config/secrets/llm.local.json`；每个业务 profile 通过 `config/endpoints/` 映射到上游模型，因此审计轨迹中 `model_profile_id` 始终是稳定的业务路由名，而 `model_upstream` 记录真正应答的模型。**把某个 profile 指向另一个模型，永远不会改写历史案例的含义。**

即使在真实模型模式下，打码依然发生在请求离开进程之前，模型依然只能提议，任何供应商故障都降级为人工审核而非放行。

## 技术栈

Python 3.12+、FastAPI、Pydantic v2、uvicorn。仅 4 个直接依赖，全部为纯 Python 且锁定版本。界面是零构建步骤的原生 JavaScript。存储为本地 JSON / JSONL——没有数据库，因为这个项目里真正有意思的问题是边界与确定性，不是持久化。
